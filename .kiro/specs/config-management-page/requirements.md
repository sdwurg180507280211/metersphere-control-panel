# 配置管理页 Requirements

## 1. 规格分类

- 类型：Feature Spec
- 工作流：Requirements-First
- 范围：为 `metersphere-control-panel` 增加一个“配置管理”页面及配套配置查询、校验、保存、应用能力

## 2. 背景

当前控制面板的核心配置主要分散在以下位置：

- `config.json`：控制面板端口、`projectRoot`、日志行数、服务清单等持久配置
- 环境变量：Redis、任务限流、超时、打包脚本覆盖等运行时配置
- 自动探测逻辑：`../metersphere`、`mvnw`、关键 `pom.xml`、打包脚本候选路径

目前这些配置主要通过修改文件或环境变量完成，页面侧仅在空状态或错误状态下提示“请检查 `config.json`”。这会带来以下问题：

1. 新电脑初始化时，用户难以判断当前项目根目录是否有效
2. 服务配置、端口、健康检查路径等关键项缺少结构化编辑入口
3. `config.json` 与环境变量的优先级、覆盖关系对用户不透明
4. 修改配置后缺少统一的校验、保存、应用、诊断流程

## 3. 目标

### 3.1 目标

- 提供一个结构化的“配置管理”页面，集中展示当前控制面板可见配置
- 提供对 `config.json` 可持久项的安全编辑与保存能力
- 提供保存前校验能力，尽可能在页面内发现路径、端口、脚本、服务定义问题
- 明确区分“可编辑持久配置”和“只读运行时配置”
- 为“保存”与“应用”建立清晰分离的用户流程，避免产生“已保存但未生效”的误解
- 为后续跨机器迁移、环境诊断和运维排障提供稳定入口

### 3.2 非目标

- 不在第一阶段提供任意环境变量在线编辑器
- 不在第一阶段提供管理员密码或敏感凭据持久化保存
- 不在第一阶段支持任意 shell 命令配置
- 不要求所有配置项都支持无重启热生效
- 不改变现有服务控制、前端构建、整体验证打包的业务语义

### 3.3 术语表

- **`projectRoot`**：`MeterSphere` 主仓库根目录，用于解析 `mvnw`、服务 `pom.xml`、前端模块和打包脚本等相对路径。
- **`serviceCatalog`**：由后端基于 `services` 配置和项目结构解析出的服务目录，用于服务控制、校验和展示。
- **`frontendModules`**：由后端解析得到的前端模块目录集合，用于构建、校验和应用后的刷新。
- **可编辑配置（editable config）**：允许页面修改并持久化回 `config.json` 的字段集合，例如 `projectRoot`、`services` 和 `package` 下的可持久字段。
- **运行时配置（runtime config）**：由环境变量、properties 文件或运行态探测结果派生出的只读配置，不允许在第一阶段通过页面直接修改。
- **解析后配置（resolved config）**：后端将 `config.json`、环境变量和自动探测结果合并、规范化后得到的最终配置快照。
- **配置草稿（draft）**：用户在页面上的本地编辑态，仅用于校验、保存和应用前确认，不应在编辑时直接影响磁盘或运行态。
- **应用配置（apply config）**：将已保存的配置快照刷新到支持动态读取的消费者，使新配置对后续任务生效的过程。

## 4. 用户与场景

### 4.1 目标用户

- 在新电脑上初始化开发环境的开发者
- 需要调整服务清单、健康检查和路径配置的维护者
- 需要确认 Redis、打包脚本、项目根目录是否生效的排障人员

### 4.2 关键场景

1. 用户首次打开页面，希望快速确认当前 `MeterSphere` 根目录是否合法
2. 用户需要调整某个服务的 `pom`、端口、健康检查路径或启动顺序
3. 用户需要修改打包脚本路径或查看当前打包脚本候选命中结果
4. 用户需要保存 `config.json` 变更，但暂时不希望立即影响当前运行任务
5. 用户需要在保存后执行“应用配置”，并明确知道哪些修改已生效、哪些需要重启控制面板

## 5. 范围定义

### 5.1 第一阶段范围

- 新增“配置管理”页签
- 展示并编辑 `config.json` 中的以下配置：
  - `port`
  - `projectRoot`
  - `maxLogLines`
  - `package` 下的可持久字段
  - `services` 服务定义
- 展示运行时只读信息：
  - 缓存模式
  - Redis 连接来源与状态
  - 任务限流与重试参数
  - 关键超时参数
  - 打包脚本候选路径
- 提供配置校验、保存、应用、诊断刷新能力

### 5.2 第二阶段候选范围

- 支持导入 / 导出配置
- 支持配置变更历史与回滚
- 支持多环境配置模板
- 支持更细粒度的权限控制与敏感项脱敏编辑

## 6. 功能需求

### 6.1 页面结构

#### FR-1 基础设置区

**用户故事：** 作为开发者，我希望在配置管理页查看和编辑 `projectRoot`、控制面板端口和日志行数，以便快速调整本地开发环境。

WHEN 用户进入配置管理页
THE SYSTEM SHALL 展示基础设置区，用于查看和编辑 `projectRoot`、控制面板端口和日志最大行数。

#### FR-2 服务配置区

**用户故事：** 作为维护者，我希望结构化维护服务配置项，以便安全调整启动依赖、端口和健康检查路径。

WHEN 用户进入配置管理页
THE SYSTEM SHALL 展示服务配置区，以结构化列表方式展示每个服务的 `name`、`pom`、`port`、`healthCheckPort`、`healthCheck`、`startOrder` 与启用状态。

#### FR-3 构建与打包区

**用户故事：** 作为打包流程维护者，我希望查看和编辑打包脚本路径及默认参数，以便快速定位构建脚本问题并修正配置。

WHEN 用户进入配置管理页
THE SYSTEM SHALL 展示构建与打包区，用于展示和编辑打包脚本路径与默认打包参数，并展示当前候选脚本解析结果。

#### FR-4 运行时信息区

**用户故事：** 作为排障人员，我希望看到运行时只读配置及其来源，以便判断当前行为是否来自环境变量覆盖或自动探测。

WHEN 用户进入配置管理页
THE SYSTEM SHALL 展示运行时信息区，用于只读展示环境变量派生的 Redis、任务、超时与缓存状态。

#### FR-5 诊断区

**用户故事：** 作为新环境初始化的开发者，我希望直接看到项目根目录、脚本和 Redis 诊断结果，以便快速发现阻塞问题。

WHEN 用户进入配置管理页
THE SYSTEM SHALL 展示配置诊断区，用于显示项目根目录、脚本、端口、Redis 与配置来源的检测结果。

### 6.2 配置加载与展示

#### FR-6 配置快照加载

WHEN 页面首次加载
THE SYSTEM SHALL 从后端获取一个完整配置快照，并拆分为可编辑配置、只读运行时配置、诊断信息与元信息。

#### FR-7 来源标识

WHEN 页面展示任意配置项
THE SYSTEM SHALL 显示该配置项的来源标识，例如 `config.json`、环境变量覆盖或自动探测结果。

#### FR-8 应用影响提示

WHEN 页面展示任意可编辑配置项
THE SYSTEM SHALL 显示该项修改后是“可热应用”还是“需要重启控制面板生效”。

### 6.3 配置编辑

#### FR-9 草稿编辑

WHEN 用户修改任一可编辑字段
THE SYSTEM SHALL 仅更新本地草稿态，而不立即写入磁盘或改变运行时行为。

#### FR-10 脏状态提示

WHEN 页面存在未保存修改
THE SYSTEM SHALL 显示“有未保存更改”状态，并允许用户执行校验、保存、重置或应用操作。

#### FR-11 服务项增删改

WHEN 用户新增、编辑或删除服务配置项
THE SYSTEM SHALL 以结构化表单方式维护服务定义，并在保存前对必要字段执行格式校验。

### 6.4 配置校验

#### FR-12 手动校验

**用户故事：** 作为修改配置的用户，我希望在保存前校验当前草稿，以便提前发现路径、端口和脚本问题而不污染磁盘配置。

WHEN 用户点击“校验配置”
THE SYSTEM SHALL 在不写入磁盘的前提下对当前草稿执行校验，并返回错误、警告、诊断信息和应用影响说明。

#### FR-13 项目根目录校验

WHEN 校验包含 `projectRoot`
THE SYSTEM SHALL 检查目标目录是否存在、是否包含 `mvnw`、以及是否至少能命中一个配置服务的 `pom.xml`。

#### FR-14 端口校验

WHEN 校验服务端口或控制面板端口
THE SYSTEM SHALL 检查端口值是否合法、是否重复，以及是否与常见运行端口冲突。

#### FR-15 打包脚本校验

WHEN 校验打包脚本配置
THE SYSTEM SHALL 检查脚本路径是否存在、是否为文件、是否具备可执行权限，并返回候选脚本命中结果。

#### FR-16 服务定义校验

WHEN 校验服务列表
THE SYSTEM SHALL 检查每个服务项的标识、名称、`pom`、端口、健康检查路径和启动顺序是否合法。

### 6.5 配置保存

#### FR-17 安全保存

**用户故事：** 作为配置维护者，我希望仅将允许编辑的字段安全写回 `config.json`，以便避免破坏现有兼容字段和仓库外文件。

WHEN 用户点击“保存配置”
THE SYSTEM SHALL 仅将可持久字段写回 `config.json`，并保证写入过程不会生成结构损坏的配置文件。

#### FR-18 保存后反馈

WHEN 配置保存成功
THE SYSTEM SHALL 返回保存后的标准化配置、最新诊断结果和保存时间。

#### FR-19 保存失败反馈

WHEN 配置保存失败
THE SYSTEM SHALL 返回结构化错误信息，并保持前端草稿内容不丢失。

### 6.6 配置应用

#### FR-20 保存与应用分离

WHEN 用户保存配置
THE SYSTEM SHALL NOT 自动假设所有改动已经热生效。

#### FR-21 手动应用

**用户故事：** 作为运维或开发者，我希望显式执行“应用配置”，以便区分“已保存”和“已生效”，并控制生效时机。

WHEN 用户点击“应用配置”
THE SYSTEM SHALL 重新装载配置快照，并刷新支持热更新的配置消费者。

#### FR-22 生效范围反馈

WHEN 配置应用完成
THE SYSTEM SHALL 明确返回哪些配置已应用、哪些配置需要重启控制面板才能生效。

#### FR-23 运行中保护

WHEN 存在与配置强相关的活动任务且本次应用可能导致运行态漂移
THE SYSTEM SHALL 拒绝本次“应用配置”，并提示用户先等待任务结束或仅执行“保存配置”。

### 6.7 诊断与可观测性

#### FR-24 手动刷新诊断

**用户故事：** 作为排障人员，我希望在修改路径或环境后重新执行诊断，以便确认最新状态而不必刷新整页。

WHEN 用户点击“重新检测”
THE SYSTEM SHALL 重新执行项目根目录、脚本、端口与 Redis 检测，并更新页面诊断卡片。

#### FR-25 运行时状态展示

WHEN 页面展示只读运行时配置
THE SYSTEM SHALL 展示当前缓存模式、Redis 是否已连接、是否处于降级状态，以及相关环境变量来源。

#### FR-26 配置元信息

WHEN 页面加载或保存后
THE SYSTEM SHALL 展示配置文件路径、最近加载时间、最近保存时间与是否需要重启。

## 7. 兼容性要求

#### CR-1 API 兼容

WHEN 引入配置管理相关接口
THE SYSTEM SHALL CONTINUE TO 保持现有 `/api/services/*`、`/api/build/*`、`/api/package/*`、`/api/jobs/*` 与 `/api/progress/*` 接口语义不变。

#### CR-2 事件兼容

WHEN 引入配置管理页
THE SYSTEM SHALL CONTINUE TO 保持现有 WebSocket 服务状态、构建日志、打包日志和任务事件行为不变。

#### CR-3 配置格式兼容

WHEN 保存 `config.json`
THE SYSTEM SHALL CONTINUE TO 兼容当前仓库已使用的配置字段命名与整体 JSON 结构。

## 8. 安全与约束

#### SR-1 敏感信息处理

WHEN 页面展示运行时配置
THE SYSTEM SHALL 对敏感字段执行只读展示或脱敏展示，且第一阶段不提供敏感凭据持久化保存能力。

#### SR-2 命令执行边界

WHEN 页面允许编辑配置
THE SYSTEM SHALL NOT 将配置管理页扩展为任意命令执行入口。

#### SR-3 文件写入边界

WHEN 页面执行“保存配置”
THE SYSTEM SHALL 仅写入控制面板仓库内的配置文件，而不直接修改同级 `../metersphere` 仓库内容。

## 9. 成功标准

- 新电脑初始化时，用户可通过页面快速判断 `MeterSphere` 根目录是否有效
- 常见 `config.json` 变更可在页面内完成，不再要求手动编辑 JSON
- 用户能够清晰分辨“已保存”和“已生效”的差异
- 配置变更不会破坏现有服务控制、前端构建和打包功能
