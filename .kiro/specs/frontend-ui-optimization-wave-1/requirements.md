# Control Panel 前端 UI 优化 Wave 1 Requirements

## Spec Metadata

- 类型：Feature Spec
- Workflow：Requirements-First
- 目标目录：`.kiro/specs/frontend-ui-optimization-wave-1`
- 参考现状：
  - `frontend/src/App.jsx`
  - `frontend/src/components/Sidebar.jsx`

  - `frontend/src/components/ServicesTab.jsx`

  - `frontend/src/styles/App.css`

## 背景

当前控制面板前端已经具备“前端构建、服务管理、整体验证打包、配置管理”四个核心工作区，并通过 WebSocket 持续推送状态、日志和任务进度。

但从现有代码结构和交互表现来看，UI 仍存在以下问题：

- 页面导航依赖内存态 `activeTab`，刷新后无法保留当前页面，也不利于深链分享与回到上次工作现场。
- 全局视觉样式以大量硬编码颜色、阴影、渐变、emoji 和动画为主，视觉调性较“热闹”，但信息层级和操作优先级不够稳定。
- 四个核心页签的信息架构不统一：有的页面以按钮网格为主，有的页面以表单或日志为主，用户很难形成稳定心智模型。
- 移动端和窄屏场景虽然有基础响应式处理，但关键状态、主操作、日志区域在不同页面中的布局策略不一致。
- 键盘可达性、焦点可见性、语义化导航、减少动态效果等无障碍能力仍不完整。
- 加载、空态、错误、成功反馈风格分散，实时状态既有 toast 也有局部提示，但缺少统一的页面级反馈模型。

本 spec 聚焦“前端 UI/UX 第一轮优化”，目标是在不改变后端 API 形状和 WebSocket 事件契约的前提下，让控制面板界面更清晰、更稳、更适合高频运维场景。

## 范围

本轮优化包含：

- 应用壳层（App Shell）与导航可达性优化
- 四个核心页签的信息架构统一
- 设计 token、颜色、间距、圆角、阴影、动效的共享化
- 响应式布局和窄屏可用性优化
- 焦点、语义、减少动态效果等基础可访问性增强
- 页面级状态反馈、空态、错误态、加载态的统一
- 页签状态与部分非破坏性 UI 状态的保留

本轮优化不包含：

- 后端接口重命名或返回结构变更
- WebSocket 事件名调整
- 引入大型 UI 组件库或强制迁移到新设计系统框架
- 全量深色模式 / 多主题体系
- 日志虚拟滚动等以性能为唯一目标的大型重构
- 修改兄弟仓库 `../metersphere`

## 关键术语

- **App Shell**：控制面板的顶层界面骨架，包含标题区、导航区、全局状态和内容容器。
- **工作区页面**：`build`、`services`、`package`、`config` 四个主页签对应的内容区域。
- **主操作区**：用户完成当前任务必须优先关注和操作的区域，例如“开始构建”“开始打包”“保存配置”。
- **次级信息区**：辅助用户判断当前状态的区域，例如日志、历史、诊断、任务状态。
- **设计 Token**：全局复用的视觉变量，例如颜色、字号、间距、圆角、阴影、动效时长。
- **非破坏性 UI 状态**：刷新后可安全恢复的界面状态，例如当前页签、日志面板折叠状态、搜索词、筛选项；不包括正在输入但未提交的敏感表单内容。

## 用户故事

### US-1 导航与上下文

作为高频操作控制面板的开发/运维人员，我希望刷新页面后仍能回到刚才的工作区，并且能从 URL 或页面结构快速看出自己当前所在位置，从而减少来回切换的认知负担。

### US-2 页面结构一致性

作为需要在“构建、服务、打包、配置”之间来回切换的用户，我希望不同页面遵循相似的信息层级和主操作布局，从而更快找到关键动作和关键状态。

### US-3 状态反馈可判断

作为执行长时间任务的用户，我希望页面能持续、稳定地反馈“当前是否在运行、最后更新到哪里、日志在哪看、失败原因在哪看”，而不是只依赖瞬时 toast。

### US-4 窄屏与键盘可用性

作为偶尔在小屏幕或仅用键盘操作的用户，我希望关键状态、关键按钮、导航和弹窗都保持可访问、可见且可操作。

### US-5 渐进式演进

作为维护该仓库的开发者，我希望这次 UI 优化能够沿用现有 React + Vite + Zustand 架构和组件拆分方式，分阶段演进而不引入大规模回归风险。

## Requirements

### R1. 导航可定位与页签持久化

- WHEN 用户首次访问控制面板且 URL 中没有显式工作区标识
  THE SYSTEM SHALL 使用稳定的默认工作区打开页面，并在后续切换时记录最近访问的工作区。
- WHEN URL 中包含受支持的工作区标识
  THE SYSTEM SHALL 打开对应页签，并让刷新后页面保持在该工作区。
- WHEN 用户切换 `build`、`services`、`package`、`config` 页签
  THE SYSTEM SHALL 同步更新浏览器地址中的轻量路由状态，而不要求引入新的后端路由。
- WHEN 用户尝试离开存在未保存配置变更的 `config` 页签
  THE SYSTEM SHALL 在真正离开前给出一致的离开确认提示。

### R2. 统一的页面骨架与信息层级

- WHEN 任一工作区页面渲染
  THE SYSTEM SHALL 以一致位置展示页面标题、简短说明、关键状态摘要和主操作区域。
- WHEN 页面同时存在主操作区和次级信息区
  THE SYSTEM SHALL 让主操作区优先占据可视焦点，次级信息区以稳定布局承载日志、历史、诊断或任务状态。
- WHEN 主操作因运行态、权限或校验条件被禁用
  THE SYSTEM SHALL 提供可读的禁用原因或引导说明，而不是仅展示不可点击按钮。

### R3. 共享视觉 Token 与控件一致性

- WHEN 共享容器、按钮、表单、标签、状态徽标和提示条渲染
  THE SYSTEM SHALL 优先使用集中定义的视觉 token，而不是在各页面样式文件中重复硬编码核心颜色、间距和阴影。
- WHEN 页面需要强调品牌感或状态差异
  THE SYSTEM SHALL 使用受控的强调色和状态色，而不是让高饱和渐变、emoji 和装饰性动画主导主要交互。
- WHEN 用户在不同页面悬停、聚焦、按压或查看禁用态控件
  THE SYSTEM SHALL 展示一致的反馈节奏和层级关系。

### R4. 响应式布局与窄屏可用性

- WHEN 页面在桌面、平板和移动端等不同宽度下渲染
  THE SYSTEM SHALL 根据断点调整导航、标题区、卡片布局和日志区域，而不产生关键内容横向溢出。
- WHEN 页面宽度受限
  THE SYSTEM SHALL 仍让关键状态摘要和当前页主操作保持在首屏可见或可快速触达的位置。
- WHEN 页面进入窄屏模式
  THE SYSTEM SHALL 允许用户自然滚动页面内容，而不是因为全局容器策略导致主内容被裁切或难以浏览。

### R5. 无障碍与键盘操作基础能力

- WHEN 导航、图标按钮、确认弹窗、搜索框和主操作按钮渲染
  THE SYSTEM SHALL 提供清晰的语义角色、可访问名称和可见焦点样式。
- WHEN 用户仅通过键盘操作控制面板
  THE SYSTEM SHALL 支持完成“切换页签、触发主操作、关闭/确认弹窗、聚焦日志搜索”等核心路径。
- WHEN 用户系统偏好为减少动态效果
  THE SYSTEM SHALL 降低或关闭非必要动画与装饰性过渡。
- WHEN 页面使用颜色表达运行状态、成功、告警或失败
  THE SYSTEM SHALL 同时提供文本、图标或标签，避免仅凭颜色区分。

### R6. 加载、空态、错误、成功反馈统一

- WHEN 页面处于初始加载、局部刷新、空数据或失败状态
  THE SYSTEM SHALL 使用统一的反馈骨架、提示文案和操作建议。
- WHEN 长时任务正在运行
  THE SYSTEM SHALL 通过页面级状态区域持续展示任务进行中、最后更新时间或当前阶段，而不是只依赖 toast。
- WHEN 操作成功、失败或被阻止
  THE SYSTEM SHALL 保持反馈文案风格一致，并让用户能够判断下一步应该做什么。

### R7. 日志与实时状态的可读性

- WHEN 页面存在日志区域
  THE SYSTEM SHALL 为日志提供一致的工具栏位置、搜索入口、清空入口和自动滚动状态表达。
- WHEN 页面同时展示运行状态与日志
  THE SYSTEM SHALL 让用户无需滚动到日志底部也能看见当前是否仍在运行、是否失败以及失败概览。
- WHEN 日志为空、被清空或尚未开始产出
  THE SYSTEM SHALL 使用明确的空态提示，而不是只显示空白容器。

### R8. 非破坏性界面状态恢复

- WHEN 用户刷新页面或短暂离开后返回
  THE SYSTEM SHALL 恢复最近访问的工作区以及已定义为可恢复的非破坏性界面状态。
- WHEN 页面恢复本地 UI 状态
  THE SYSTEM SHALL 避免恢复可能与服务端真实运行态冲突的临时提交状态。
- WHEN WebSocket 短暂重连后页面重新同步数据
  THE SYSTEM SHALL 让界面状态恢复与实时数据恢复保持一致，而不制造“页面显示已完成但任务仍在运行”之类的冲突观感。

### R9. 渐进式交付与实现约束

- WHEN 本轮 UI 优化实施
  THE SYSTEM SHALL 继续沿用现有 React、Vite、Zustand 和 CSS 文件组织方式，避免为本轮优化强制引入大型第三方框架。
- WHEN 需要加入路由同步或共享 UI 状态
  THE SYSTEM SHALL 优先采用轻量实现方案，与现有单页结构保持兼容。
- WHEN UI 优化按阶段交付
  THE SYSTEM SHALL 允许先落共享壳层和样式基础，再逐页推进信息架构和交互细节优化。

### R10. 兼容性要求

- WHEN 本轮优化完成
  THE SYSTEM SHALL CONTINUE TO 保持现有服务控制、前端构建、整体验证打包、配置保存/应用和日志查看主流程可用。
- WHEN 前端界面重构共享组件或样式结构
  THE SYSTEM SHALL CONTINUE TO 保持现有 API 路径、主要响应结构和 WebSocket 事件名不变。
- WHEN 页面布局和视觉样式变化后
  THE SYSTEM SHALL CONTINUE TO 允许用户完成现有快捷键与核心运维操作，不把高频能力隐藏到难以发现的位置。
